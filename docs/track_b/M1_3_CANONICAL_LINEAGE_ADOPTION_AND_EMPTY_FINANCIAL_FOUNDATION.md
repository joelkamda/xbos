# XBOS Track B M1.3 — Canonical Lineage Adoption and Empty Financial Foundation

**Record type:** Persistence implementation and rehearsal record

**Workstream:** Track B-FIN — Neutral Financial Spine

**Phase:** M1.3

**Status:** Candidate package; activation not yet authorized

**Date:** 6 August 2026

**Predecessor:** M1.2 clean-room source-state reconstruction at `5f01634`

## 1. Outcome

M1.3 creates a candidate single canonical Alembic lineage with two ordered facts:

1. `m13_source_state_001` — the approved M1.2 source-state baseline;
2. `m13_financial_foundation_002` — the empty neutral financial foundation.

The package proves both routes that XBOS must support:

- reconstruct the complete database from nothing and upgrade to the M1 head;
- recognize a verified source-state database, replace only its migration stamp, and apply the same M1 head additively.

It does not switch the normal `alembic.ini`, edit the four historical migration files, seed financial event types, emit events, transform data, change application writers, or activate canonical models.

## 2. Why the lineage remains a candidate

The current active Alembic files cannot reconstruct the approved source schema from an empty database. M1.2 proved an exact source-state reconstruction separately. M1.3 builds the future authority from that proof without changing the working application while rehearsal is underway.

Promotion of `alembic_neutral.ini` to the sole project migration authority is a separate gate. Promotion occurs only after both rehearsal paths pass, the schema is reviewed, and the project owner authorizes activation.

## 3. Approved M1 scope

M1.3 installs 15 empty tables:

| Area | Tables |
|---|---|
| Organization and policy | `organization_units`, `currency_assets`, `tenant_currency_policies`, `business_cycle_policies` |
| Source and parties | `kernel_source_records`, `financial_counterparties` |
| Operational value accounts | `operational_financial_accounts`, `payment_provider_accounts` |
| Reliability | `idempotency_records`, `outbox_messages` |
| Financial facts | `financial_event_type_versions`, `financial_events`, `financial_event_taxonomy` |
| Historical migration evidence | `historical_transformation_runs`, `historical_transformation_exceptions` |

The event catalog and event store are intentionally empty. Catalog seeding and the transactional event engine belong to M2.

## 4. Superseding naming decision

The final B2 migration record supersedes the physical blueprint’s earlier `canonical_backfill_*` terminology. M1.3 therefore uses:

- `historical_transformation_runs`;
- `historical_transformation_exceptions`.

These records support controlled conversion of retained source history. They are not a parallel operational model and do not preserve old application contracts.

## 5. Principal invariants

- New internal identifiers are `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Public identifiers are UUIDs generated by PostgreSQL.
- Money is `NUMERIC(24,8)` and time instants are `TIMESTAMPTZ`.
- Tenant-owned relationships use composite foreign keys.
- `users` and `taxonomy_nodes` receive safe additive `(tenant_id,id)` unique keys to support tenant-safe references.
- Retained financial authorities use `ON DELETE RESTRICT`, never cascade deletion.
- Catalog versions, financial events and event classifications are append-only.
- Financial event amount policy is checked from the catalog on insert.
- Outbox identity and payload are immutable while delivery state remains mutable.
- M1 contains no event-type seed rows and no financial events.

## 6. Rehearsal safety

The verifier accepts only local PostgreSQL hosts and exactly these disposable database names:

- `xbos_track_b_m13_fresh_test`;
- `xbos_track_b_m13_adoption_test`.

It refuses arbitrary database names. A successful run drops both databases. A failed run retains only the failed disposable database for inspection and prints its exact name. Cleanup also requires the exact name as confirmation.

The verifier never targets the normal XBOS database, the parity database, or a production host.

## 9. Downgrade boundary

Before use, the empty M1 structures have a reviewed down migration. The source-state root is not destructively downgraded; a disposable database is dropped by explicit name instead.

Once canonical financial facts exist in a later slice, destructive schema rollback is no longer the financial correction mechanism. Financial corrections proceed forward through canonical events and approved operational procedures.

## 10. Exit gate

M1.3 is complete only when:

- static contracts pass;
- fresh reconstruction reaches the M1 head;
- existing source-state adoption reaches the identical head;
- no source-state table is removed during adoption;
- composite tenant references reject cross-tenant links;
- financial event update and delete are rejected;
- the empty M1 structures downgrade and upgrade cleanly;
- both disposable databases are absent after the run;
- the full test suite remains green;
- the worktree contains only reviewed M1.3 changes.

Passing this gate authorizes review of lineage activation. It does not itself authorize application writes or historical transformation.
